## 🔴 High Issues

### H-001 · `src/app/dashboard/page.tsx` · Line ~180 — `ProjectDrawer` prop mismatch

**What is broken:**  
`ProjectDrawer` in `src/components/dashboard/ProjectDrawer.tsx` defines its `metrics` prop as:

```ts
metrics: [string, string, boolean?][]; // [label, value, isPrimary?]
```

But in `dashboard/page.tsx`, the call passes:

```ts
metrics: selectedProject.stats.map(([k, v]) => [k, v])
```

`ProjectCardData.stats` is typed as `[string, string][]` (only 2 elements), so `.map(([k, v]) => [k, v])` produces the correct 2-element tuple. However, the call **also hard-codes** a third boolean as `undefined` is missing from the `.map()`. The real problem is that `ProjectCardData` does not have a `ticker` field on its export type — only the internal type alias uses it. Actually, `ProjectCardData` does have `ticker: string`. The actual runtime issue: the `metrics` shape from `ProjectCard.stats` is `[string, string][]` but `ProjectDrawer` expects `[string, string, boolean?][]`. A third element will always be `undefined` at the third position. Additionally, `ProjectDrawer` accesses `.length` on `selectedProject.stats` directly but only maps `[k, v]` — this works at runtime but is a type-imprecision mismatch.

**Fix applied:**  
In `dashboard/page.tsx`, changed the metrics map to include the third optional boolean (all `false` by default):

```ts
metrics: selectedProject.stats.map(([k, v]) => [k, v, false] as [string, string, boolean?]),
```

Also, `dappUrl: "#"` in the drawer call is a broken link — confirmed a placeholder.

### D-007 · `ProjectCard.tsx` — `Badge` component uses non-existent Tailwind colors

**Status:** ✅ No issue — Tailwind v4 auto-generates color utilities from CSS variables.

### D-010 · `leaderboard/page.tsx` — `parseFloat` on "—" values (NaN)

**File:** `src/app/leaderboard/page.tsx`  
**Lines:** ~130-140  
**What:** Sort comparator:
```ts
parseFloat(a.volume24h.replace(/[^0-9.]/g, ""))
parseFloat(a.users.replace(/[^0-9.]/g, ""))
```

When `volume24h = "—"` or `users = "—"`, `replace` returns `"—"`, and `parseFloat("—")` returns `NaN`. Sorting with NaN produces unpredictable results. However, since `"—"` entries have `tvlNum: 0` (used for TVL sort) or `growthNum: 0` (used for growth sort), they only hit this path for `volume` and `users` sorts.  
**Severity:** Low — NaN comparisons are consistently falsy, pushing `"—"` entries to end of sorted list. Works in practice.  
**Recommendation:** Add fallback: `parseFloat(...replace(...)) || 0`.
